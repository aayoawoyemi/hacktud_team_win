# PRD: Office compute pool (working name)

Living document. The orchestrator session (Aayo's main Pi) edits this file. Research workers propose changes in
their check-ins under "PRD suggestions"; they do not edit this file directly.

Last updated: Sat Nov 7, 3:55pm CT (HackUTD 2026 "Zero Day"; Devpost team registration by 11pm Sat, submission 12pm Sun)

## One line

Pool the computers a team or office already owns into one private AI server, so data never leaves the building.

## Problem

- Small regulated offices (mortgage brokers, clinics, law firms, insurance agencies) want AI on client data but cannot
  or will not send that data to a cloud model.
- They already own several laptops/desktops that sit mostly idle. No single one can run a useful model well.

## Demo hardware (this weekend)

- **3 MacBooks** (Apple Silicon): M5 24 GB (Aayo), M3 16 GB, and a third with 24 GB (chip TBC). About 64 GB total.
  Personal machines, not clean: limited disk, other apps open. No Dell/Windows machines and no NVIDIA GPUs at the venue.
- Older Windows/Dell office machines are the **customer story and roadmap**, not the demo.
- Network: a teammate brings a travel router (confirmed). A router with no internet still makes a LAN; internet is
  only needed to download models, so download them early. EXO needs IPv6 multicast (`ff12::e0a1:de89` UDP 52413) plus
  TCP 52414 / HTTP 52415 between Macs, has no static-peer fallback, and needs macOS "Local Network" allowed.
- Old network note: bring our own travel router or gigabit switch plus USB-C Ethernet adapters. Do not depend on venue Wi-Fi:
  campus Wi-Fi often isolates clients and blocks multicast/mDNS, so machines may not see each other (EXO README says
  guest/office Wi-Fi breaks its discovery).
- Thunderbolt 5 (M4 Pro/Max MacBook Pro or newer, macOS 26.2+) enables RDMA between Macs; Airs and base-chip MacBook
  Pros fall back to TCP.

## Scope (to be filled from research)

### Must have (demo)

- [ ] Route: each Mac runs a whole model; requests go to a free Mac (an office has many users at once, so this is
      where the throughput is)
- [ ] Pool as the wow moment: `mlx-community/Qwen3.6-35B-A3B-4bit` (20.4 GB, 40 layers, EXO built-in card), pipeline,
      `min_nodes=3` (EXO otherwise uses the fewest Macs that fit). 6-bit build (~28-29 GB) is bigger than any one Mac's RAM:
      the strongest "no laptop can run this" claim if it fits. Fallback `Qwen3-30B-A3B-4bit` (17.6 GB). Stretch
      `Qwen3-30B-A3B-8bit` (33.3 GB, needs all 3 with apps quit). Too big for our 64 GB: Qwen3-Next-80B, gpt-oss-120b,
      every "Flash" model (DeepSeek-V4-Flash 155 GB).
- [ ] Disk: EXO downloads the WHOLE model to every Mac -> ~25 GB free per Mac. Pre-download tonight, copy over LAN, `--offline`
- [ ] First hour: quit heavy apps; read per-Mac `ram_available` and `gpu_working_set` from EXO `GET /state`; preview
      placement with `/instance/previews` before the demo
- [ ] First 2 hours: pool Qwen3.6-35B-A3B 4-bit on 2 Macs with Parallax and with EXO side by side, record t/s, pick one
- [ ] Demo-day memory checklist: quit apps; `sudo sysctl iogpu.wired_limit_mb=19456` (24 GB Macs) / `11264` (16 GB Mac);
      context 4K-8K. Default GPU limit is 2/3 of RAM (16 GB Mac: 10.9 GB; 24 GB: 16 GB); pool ~31-37 GB with apps
      open, ~46-49 GB with apps quit and the limit raised
- [ ] First hour: run `llama-bench` (8B Q4_K_M) on every Mac and ping between them; record the numbers here

- [ ] Place layers by measured speed, not memory share; a slow device can get zero layers (prima.cpp: EXO-style
      memory-share placement gave an M1 9 of 32 layers -> 263 ms/token vs 15 ms on the best single device)

### Why pooling works (pitch backbone)

- Even NVIDIA's B200 kernel competition (GPU MODE NVFP4, grand prize for "closest to speed of light") scores batch-1
  4-bit decode against DRAM bandwidth. Bandwidth is the resource, so we pool it.

- Generating each token reads every active weight once, so speed is set by memory bandwidth, not compute. Even a 1.8x
  tensor-core unlock on an RTX 3090 (Oct 2026 gpu-unlock) left decode speed unchanged. The resources worth pooling
  are memory capacity and memory bandwidth.
- No single office laptop can hold a useful model; the pool can. Pooling buys capacity; routing buys throughput for
  many users at once. Neither makes one request faster than a machine that already fits the model.

### Later (roadmap, not this weekend)

- Groups of organizations that trust each other (credit unions, franchise branches), then smart contracts / payments
- Device trust levels, signed jobs, tamper-evident audit log
- Node authentication and encryption (EXO has none: plain Zenoh TCP, random node ids, any same-build Mac on the LAN joins)
- Prompt reading on the newest chip, generation on the highest-bandwidth chip (HexGen-2 style) for long documents
- Optional prefill speed-up on customers' GeForce cards; do NOT ship the firmware unlock (trust story)

## Open questions

1. ~~Route or pool?~~ Leaning: route first, pool as the wow moment (principles-01). Splitting by layers adds
   capacity, not speed: each extra node costs ~5 ms/token on 2.5 GbE, 10-30 ms on Wi-Fi.
2. Build on EXO, llama.cpp RPC, MLX distributed, distributed-llama, prima.cpp, or our own layer on top of one of them?
   Note: "EXO" now means exo 1.0 (rewrite; MLX-only, Apple-first; v1.0.71). The 2024 tinygrad/gRPC version most
   Reddit posts describe is gone. All Macs must run the same exo build or they refuse to join.
   Test order: Parallax first, EXO 1.0 second, llama.cpp RPC as fallback and Windows customer path. Dropped:
   distributed-llama (2^n nodes only, so 3 Macs -> 2), prima.cpp (stale fork, Qwen3.6 support unverified).
   Parallax: Qwen3.6-35B-A3B MLX supported (#473), web UI, `parallax join`, OpenAI API, routing + continuous batching
   on Mac. Caveats: budgets 0.5 x RAM per Mac (pool 32 GB), mDNS flaky on macOS (pass scheduler address), use LAN mode
   + `-u` (no telemetry, no public relay) for the privacy story.
   EXO is usable as a black box over HTTP (OpenAI API, placement and state endpoints) and already routes requests to
   the least-busy instance. New candidate: Parallax (GradientHQ, arXiv 2509.26182): MLX on Mac, layer split,
   continuous batching, per-request routing; up to 3.6x throughput vs HexGen.
3. What tokens/sec is realistic? Estimates (principles-01): 8B Q4 ~17.5 t/s on one base M4, ~37 on M4 Pro;
   split over 2 Macs 11-16 t/s. Tensor parallel only pays off with TB5 RDMA (EXO: Qwen3 235B 19.5 -> 31.9 t/s, 1 -> 4
   Mac Studios); over Wi-Fi it is 5-20x slower. Measured: ~150 ms per all-reduce over Wi-Fi (distributed-llama in
   the prima.cpp paper) -> 8B at 1.15 s/token. Tensor parallel is ruled out on Wi-Fi.
4. Customer story: how do Windows/Dell machines join? EXO cannot (POSIX-only code, no MLX on Windows, Mac+Linux mixes
   refused by design). A Dell CPU decodes 8B at ~5-10 t/s, so in a layer split it slows every token; better as a
   routed worker running its own small model. Candidate path: llama.cpp (runs on Windows) behind our router.
