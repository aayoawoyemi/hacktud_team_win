Office compute pool: how it works

An explainer for the HackUTD 2026 team. It covers why one laptop can't run a useful AI model, how several laptops can run one together, and what that costs in speed. The numbers come from the research sessions' sources (linked at the bottom). Anything marked estimate is calculated, not measured.

1. Why one laptop isn't enough

A model has to sit in memory to run. On a Mac the GPU shares the main memory (unified memory), but macOS lets the GPU use only part of it, about two-thirds on a 16 or 24 GB Mac. Other open apps take more. Turn Macs on and off to see which models fit.

Usable GPU memory per Mac estimate: two-thirds of RAM minus 2 GB for open apps. The limit can be raised with sudo sysctl iogpu.wired_limit_mb=.... Model sizes are for 4-bit versions, which store each weight in about half a byte instead of 2 bytes.

2. What one token costs

The model writes one word-piece (a token) at a time. For every token the chip reads every weight it uses from memory once, so memory bandwidth (GB per second) sets the speed, not raw compute. That's why the RTX 3090 "unlock" in October 2026 gave 67% more math speed but left chat speed unchanged.

  • Dense model (e.g. Llama 70B): reads all weights for every token.
  • Mixture of experts, MoE (e.g. Qwen3-30B-A3B): has many small "expert" blocks and uses only a few per token, so it reads about 2 GB per token even when the whole model is 18 to 45 GB. That's why a MoE model is the right pick to pool: it needs a lot of memory, but each token is cheap.

Estimate: time per token = GB read per token ÷ (bandwidth × 70%). Real runtimes reach 55 to 78% of the chip's bandwidth (llama.cpp Apple Silicon benchmarks, discussion #4167).

3. Routing vs pooling

  • Routing: every Mac holds a whole small model. Each request goes to whichever Mac is free. Three Macs serve three people at once. This adds throughput.
  • Pooling: one big model is cut into slices, and each Mac holds a slice. Every token passes through all the Macs in turn. This adds capacity: the office can run a model no single machine can hold. Each hop between Macs adds network delay, so one request is never faster than on a single machine that could fit the model.

The plan is to do both: route small requests, and pool one big MoE model as the demo moment. EXO already does both in one cluster, with the model field of each request picking which.

5. The network

The Macs need to reach each other directly. They don't need the internet, except to download models beforehand. A travel router plugged into nothing still creates a private local network (a LAN).

Estimate: each Mac's share of the token's reading time (split by its share of the model), plus one hop delay per Mac (the token loops back to the first Mac). Hop delays include software overhead: about 5 ms per hop was measured on 2.5 GbE (Geerling, Dec 2025), 10 to 30 ms on Wi-Fi. Real speed is usually lower than this ideal.

Venue Wi-Fi risk: campus networks often block devices from seeing each other. EXO finds peers through IPv6 multicast only and has no manual "connect to this IP" fallback today, so if the venue blocks it, EXO won't form a cluster. That's why the travel router is required.

6. Who gets which layers

Giving each Mac layers in proportion to its memory sounds fair but can be badly slow. The slowest Mac holds up every token. In the prima.cpp paper, memory-share placement gave an old M1 9 of 32 layers and the pool ran at 263 ms per token, against 15 ms on the best single device alone. Placing layers by measured speed, and letting a slow device get zero layers, cut time per token by up to 31x.

What EXO does: splits by free memory only, and gives every Mac in the group at least 1 layer. With an A3B MoE model and nothing swapping, the M3's share should cost about 4 ms per token estimate, so the prima.cpp slowdown is unlikely for us. A Mac can be told to lend less memory with OVERRIDE_MEMORY_MB, which could drive a "how much memory this laptop lends" slider in the UI.

Glossary

  • Token: a word-piece. Speeds are in tokens per second (t/s); reading speed is about 10 t/s.
  • Prefill vs decode: prefill reads the prompt (fast, compute-heavy); decode writes the answer one token at a time (limited by memory bandwidth).
  • Quantization (Q4, 4-bit): storing weights with fewer bits, so the model is about 4x smaller with a small loss in quality.
  • Unified memory: on Apple Silicon, the CPU and GPU share one pool of RAM.
  • Memory bandwidth: how fast the chip can read memory. M3: 100 GB/s, M5: 153 GB/s.
  • MoE (mixture of experts): a model that uses only a few of its blocks per token. It is big to store and cheap to run.
  • Pipeline / tensor parallel: split by layers vs split inside each layer (section 4).
  • All-reduce: every machine sends its partial result and gets back the combined result.
  • RDMA: one machine writes straight into another's memory, skipping most software. On Macs this needs Thunderbolt 5 and macOS 26.2+.
  • MLX / llama.cpp: the two main engines that run models on Macs. EXO uses MLX.
  • EXO: open-source software that pools Macs into one AI cluster. Version 1.0 is Mac-only.
