1. What Oasis is

Aayo · 0:00 to 0:30

Good afternoon. We are Oasis. Oasis distributes LLM inference across idle GPUs, pooling memory over a private, offline network to run models no single device can hold, and in doing so makes private AI available to small organizations on hardware they already own.

In practical terms, a small company that deals in law or healthcare could use the computers lying around its office to build a mini home lab using our protocol. These three MacBook Airs, this router and this switch are that lab. At this moment they are serving a 25-gigabyte language model, and none of them is connected to the internet.

2. The three problems

Aayo's brother · 0:30 to 1:45

Oasis addresses three problems: the scarcity of compute, the privacy of data, and access to AI together with the waste of existing hardware.

The first is scarcity. Demand for GPUs and for inference has grown faster than supply, and both now sell at a premium. For running a large model, the binding constraint is memory. A model's weights must fit in GPU memory before it can answer a single question, and a machine with enough memory to hold a capable model costs thousands of dollars. For most small organizations, that cost is prohibitive.

The second is privacy. Firms in law and healthcare hold client and patient records that they cannot send to a third-party cloud service. For these firms, cloud inference is excluded by obligation rather than by preference, and a dedicated server is excluded by cost. In practice, they go without.

The third concerns access and waste. These same offices already own computers with capable GPUs. Most of that capacity sits idle through the working day, and the machines are eventually replaced and discarded. Any one of them is too small to hold a strong model, but together they have enough memory. Oasis treats the hardware an office already owns as a single resource, so the capacity it has already paid for is put to use rather than wasted.

3. Live demo and how it works

Preston · 1:45 to 3:20 · explain it in your own words, don't read it
Read this beforehand: how Oasis works, end to end

The machines. The M3 Air (16 GB, 192.168.8.113) is main. It runs the SpacetimeDB database called pool, the coordinator, and llama-server, and it is the only machine that holds the model file. The two M5 Airs (24 GB each) are helpers. Each runs our agent, and the agent starts llama.cpp's rpc-server when the database tells it to. The helpers never download the model. Main sends each helper its layers over the cable at load time, and the helper caches them on disk so the next load is faster.

How the model is split. A language model is a stack of layers, and a token is produced by passing data through every layer in order. llama.cpp splits that stack into contiguous blocks, one per machine, sized to each machine's free GPU memory. For the 26B, main holds about 5.7 GB and each M5 holds about 9.9 GB. To produce one token, main runs its block and sends a small vector of activations to the first helper. That helper runs its block and passes the result to the second helper, and the result returns to main, which picks the next token. Every token therefore visits every machine. Memory adds up across the pool, but speed does not, which is why the pool is wired: each hop on Ethernet takes under a millisecond. The model is also mixture-of-experts, so each token reads only about 4B of its 26B parameters, which is why 12.5 tokens per second is possible on fanless laptops.

What we built: the control plane. llama.cpp does the math. Everything that decides who does what is ours, written in Rust, and the whole state of the pool lives in SpacetimeDB. SpacetimeDB is a database that also runs our code. Our module defines tables (node, heartbeat, command, split_plan, cluster_status, event, model_request) and reducers, which are the only functions allowed to change those tables. Every client subscribes and sees each change live, so there is no separate server or status API.

How the pool starts. When an agent starts, it registers. A row appears in node with that machine's GPU memory, and from then on it writes a heartbeat every second. The coordinator watches these tables. Once enough helpers are ready, it computes a split plan in proportion to each machine's memory and writes it to split_plan (state PLANNED). Next it writes a command row for each helper telling it to start its rpc-server (STARTING_HELPERS). Each agent sees its command, starts the server, and reports back that it is listening. The coordinator then launches llama-server pointed at the helpers (LAUNCHING), and once the model has loaded and answers a health check, the state becomes SERVING. The sequence is EMPTY, PLANNED, STARTING_HELPERS, LAUNCHING, SERVING, and the database itself rejects any illegal jump between states. Nobody types commands on the helpers.

Join, switch, failure. When a new laptop starts its agent, it registers like the others. The pool keeps answering until the new machine is ready, then re-splits across all of them in one model reload. Switching models is one call to the request_model reducer, and the coordinator re-plans for the new model. If a helper disappears (for example, a laptop goes to sleep), llama.cpp aborts. The coordinator sees this, re-plans on the machines that remain and relaunches without anyone intervening.

The dashboard is one HTML page. Every second it reads the database with SQL and sends chat to llama-server. It only reads, and it never changes the pool's state.

4. Results and close

Aayo · 3:20 to 4:00

All of these measurements were taken on these three machines with no internet connection. Gemma 4 26B occupies 25.0 gibibytes. The largest laptop here can allocate 17.8 to a model, so the model is 1.4 times larger than any single machine. The pool serves it at 12.5 tokens per second, with 0.6 seconds to the first token, and completed 9 of 9 benchmark requests.

Pooling also sustains throughput. On the smaller 12B model, one fanless Air falls from about 16 to 8 or 9 tokens per second as it heats up, while the pool holds about 11 for minutes. The round trip between machines is under a millisecond on Ethernet, and the network costs about $140.

Likely questions

Anyone · one or two sentences each

Is the pool faster than one machine? For memory, yes, because it runs models that none of the machines can hold alone. Under sustained load, three Airs hold 11 to 12.5 tokens per second while a single Air throttles to 8 or 9. Speculative decoding adds 1.6 to 1.7 times on rewrite tasks (measured on the 12B, one machine).

Why not Wi-Fi? It works, but every token crosses every machine, so latency accumulates. Ethernet is under a millisecond per hop, and the venue Wi-Fi also blocked traffic between laptops.

What if a laptop dies? llama.cpp aborts. Our coordinator detects it, then re-plans and relaunches on the remaining machines automatically.

Why SpacetimeDB? The registry, heartbeats, commands, live status and history are all tables and subscriptions, so there was no server or status API to write, and the database rejects illegal state changes.

Why Rust? It is one language from the database module (WebAssembly) to the agents. Generated bindings turn a schema mismatch into a compile error, and each machine runs one binary.

Is this EXO? It shares the idea of pooling devices. Oasis is an offline kit for hardware an office already owns, with SpacetimeDB holding the cluster state. Oasis is the pooling protocol and orchestration, and llama.cpp runs the math.

Security? The pool sits on its own router with no internet. llama.cpp's RPC has no authentication, so it must stay on a private network. Encrypted links are next.

How far does it scale? Memory adds up. By our calculation, which we have not run, about eight RTX 3090s would hold DeepSeek V4 Flash at near-native precision.

Don't claim: "first to pool laptops", kernel speedups, "$100", or "recovers in seconds".
